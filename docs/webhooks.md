# События: подпись, приёмник, conformance

Цепочка одна: транзакция Akeda → transactional outbox → диспетчер → подписанный
webhook → ваше расширение → обычная команда Akeda через публичный API.

Событие сообщает о **свершившемся факте** и командой не является. Тело — минимум
о факте, а не документ: подписчику, которому нужны подробности, идти за ними в
API под своими правами, и кабинет видит этот поход.

## Подпись

Машинный контракт — `snapshot/extension-delivery/v1/delivery-contract.json`.
Он собран из живых констант диспетчера и несёт синтетические векторы, по которым
вы проверяете свою реализацию, ничего не запуская у нас.

Заголовки (все пять входят в подписываемую строку — неподписанных заголовков в
доставке нет намеренно):

```
Akeda-Signature:            v1=<hex(hmac)>
Akeda-Signature-Key-Id:     whk_…
Akeda-Signature-Timestamp:  <unix seconds>
Akeda-Installation-Id:      <uuid>
Akeda-Event-Id:             <uuid>
```

Подписываемая строка — шесть полей через `\n`:

```
<version> \n <keyId> \n <timestamp> \n <installationId> \n <eventId> \n <sha256hex(body)>
```

Тело входит **дайджестом**, а не целиком: получателю не приходится удерживать
весь запрос в памяти, а разделитель не может встретиться внутри подписываемых
данных и склеить два поля в одно.

Алгоритм — HMAC-SHA256, окно свежести — 300 секунд, **двустороннее**: подпись
«из будущего» дальше окна отклоняется так же, как просроченная.

## Пять правил приёмника

**1. Сырые байты.** Дайджест считается по тому, что пришло. `express.json()`,
разбирающий тело до вас, ломает проверку подписи — включайте raw body.

**2. Порядок проверок: сначала HMAC, потом окно.** Обратный порядок даёт тому, у
кого ключа нет, различимый по ответу способ нащупать границу окна и подобрать
момент для переигрывания перехваченного запроса.

**3. Ключ выбирается ПО идентификатору, а не перебором.** Перебор принял бы
подпись, сделанную ключом, который отправитель не называл, и стёр бы
единственный отказ, по которому видно, что вы остались на секрете с кончившимся
перекрытием ротации. Держите оба ключа, пока перекрытие идёт: между тем моментом,
когда Akeda завела новый секрет, и тем, когда вы выкатили его в свой приёмник,
проходит ВАШ релиз.

**4. Сверьте заголовки с телом.** Вы выбираете ключ и дедуплицируете повтор по
заголовкам ДО разбора тела. Если заголовок обещает одно событие, а тело несёт
другое, дедупликация защищает не тот факт, который приняли.

**5. Проверьте кабинет.** Подпись сошлась — это ещё не «событие моё». Установка
принципал ОДНОГО кабинета, и самая частая ошибка приёмника — один секрет на все
установки: подпись сходится, а проверка кабинета выпадает целиком.

И два правила про ответ:

**Отказ окончательный.** Подделка получает `4xx`, а не `5xx`: ответ `5xx`
заставит Akeda повторить подделку пятнадцать раз, а `2xx` означает, что вы её
приняли.

**Повтор — норма.** Отказ на повтор превращает каждую штатную попытку в мёртвое
письмо. Факт применяется один раз на `event_id`, а `2xx` возвращается и на
первую доставку, и на все следующие.

## Ваш код

Проверку не надо писать заново: она есть во всех трёх клиентах и проверена теми
же векторами, что лежат в контракте.

```ts
const { envelope } = verifyWebhook(request.headers, rawBody, { keys });
```

```python
envelope = verify_webhook(dict(request.headers), raw_body, keys)
```

```go
envelope, _, err := akeda.VerifyWebhook(request.Header.Get, body, keys, time.Now(), 0)
```

Целиком — `examples/webhook-receiver-go`, `examples/webhook-receiver-python`,
`examples/typescript/receiver.ts`. Все три проходят весь набор проверок.

## Conformance

```bash
AKEDA_CONFORMANCE_SIGNING_SECRET='whs_…' \
  go run ./cmd/akeda conformance run examples/extension/target.json
```

Секрет берётся из окружения или из файла описания: флага со значением секрета у
инструмента нет и не будет — `argv` процесса виден любому пользователю машины
через `ps`.

Набор **сам становится диспетчером** и бьёт по вашему приёмнику теми же байтами,
что уедут в бою. Живая Akeda ему не нужна и вредна: прогон против стенда
проверял бы заодно нашу сеть, наши квоты и наш журнал — то есть то, за что вы не
отвечаете и чего не можете починить, а красный набор перестал бы означать
«почини свой приёмник».

Что проверяется:

| Проверка | Что делает |
|---|---|
| `signature/accepted` | законная доставка |
| `delivery/answer-within-deadline` | меряет задержку ответа |
| `signature/tampered-body` | меняет тело после подписи |
| `signature/wrong-secret` | тот же ключ, чужой секрет |
| `signature/unknown-key-id` | ключ, которого приёмник не знает |
| `signature/absent` | доставка без заголовков подписи |
| `signature/unknown-version` | версия схемы подписи `v2` |
| `signature/stale-timestamp` | подпись старше окна |
| `signature/future-timestamp` | подпись из будущего |
| `envelope/header-body-mismatch` | заголовки про одно событие, тело про другое |
| `isolation/foreign-installation` | конверт чужой установки, чужой ключ |
| `isolation/foreign-installation-own-key` | чужая установка, СВОЙ ключ |
| `retry/duplicate-accepted` | точный повтор запроса |
| `retry/resigned-attempt` | тот же `event_id`, новая подпись |
| `deadletter/unknown-event-type` | подписанное событие незнакомого типа |
| `idempotency/effect-applied-once` | две доставки одного события |

Последняя требует `effectProbeUrl` — ручки вашей ОТЛАДОЧНОЙ сборки, отвечающей
на `GET ?event_id=…` телом `{"applied": N}`. Ответ `2xx` на повтор доказывает,
что приёмник повтор принял, и ничего не говорит о том, применил ли он факт
второй раз: последствие живёт в вашей базе. Ручки нет — проверка **пропущена** и
пройденной не считается. В боевой сборке такой ручки быть не должно: она
отвечает на вопрос «применял ли ты этот факт», а такой ответ никому снаружи не
положен.

## Чего набор проверить не может

Обратное направление — расширение как клиент нашего API — снаружи непроверяемо:
там сервером обязана быть Akeda, и подставить вместо неё заглушку значит
проверить заглушку. Набор объявляет это пропусками и печатает их так же громко,
как отказы:

- `launch-token/single-use` — второе предъявление токена запуска гасит Akeda;
- `launch-token/lifetime` — срок назначает Akeda;
- `installation-token/rotation` — токен выдаёт и отзывает Akeda;
- `delivery/journal-and-replay` — журнал и повтор наружу не открыты, а исчерпать
  попытки нельзя: расписание растянуто на 26–39 часов.

Всё это проверяется на стенде разработчика, **когда он появится**. До тех пор
пропуск остаётся пропуском, а не тихим «пройдено».

## Что происходит, когда приёмник молчит

Установка паркуется после **трёх мёртвых писем подряд**. Любая удачная доставка
обнуляет счётчик. Парковка **приостанавливает** доставку: наряды копятся, в
мёртвое письмо не уходят. Токены, секрет подписи и настройка не трогаются —
парковка не отзыв.

Выход из парковки — та же проверка живости (`2xx` по `runtime.healthUrl` в срок)
и **кнопка**: автоматического выхода нет. Снятие парковки выпускает накопленное,
и решение выпустить трёхдневный завал платформа не принимает по одному ответу от
машины, которая только что встала. Цена названа честно: приёмник, починенный
ночью, стоит до утра.

Приложение, у которого больше половины работающих установок запарковано (от трёх
установок), перестаёт предлагаться новым кабинетам. Стоящие установки при этом
работают и обновляются — обновление на исправленную версию и есть лечение.
